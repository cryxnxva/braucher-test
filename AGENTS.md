# Правила проекта BRAUCHER (тестовое задание)

Обязательные правила для всех, кто пишет код в этом репозитории, включая
код-агентов. Нарушение любого пункта — причина остановить работу и исправлять.

## Зависимости

- Разрешены только библиотеки, перечисленные в `requirements.txt`:
  `requests`, `python-dotenv`, `gspread`, `pytest`.
- Добавлять новые пакеты запрещено. Нужна ещё одна библиотека — сначала вопрос
  заказчику, потом изменения `requirements.txt`.
- Python 3.11 или новее.

## Секреты

- Все секреты читаются только из `.env`, единственная точка доступа — `common.py`.
  В остальных модулях обращение к `os.environ` с токеном недопустимо.
- Содержимое `.env` и `credentials.json` нигде не выводится: не в логи, не в
  исключения, не в дампы, не в комментарии, не в ответ пользователю.
- `task.md` и `vacancy.md` не коммитятся: в них есть действующий API-токен.
- Значения `.env.example` — только пустые заглушки и публичные артикулы.

## Работа с Wildberries API

- Токен передаётся в заголовке `Authorization` строго БЕЗ префикса `Bearer`:
  `Authorization: <WB_TOKEN>`.
- Все HTTP-запросы к API Wildberries идут только через `wb_get` / `wb_post` из
  `common.py`. Напрямую вызывать `requests.get` / `requests.post` в скриптах
  запрещено — иначе теряются ретраи и обработка лимитов.
- Имена полей в ответах API брать ТОЛЬКО из реальных сырых дампов в `output/`.
  По памяти, по документации или по аналогии с другими эндпоинтами — нельзя.
  Сначала дамп, потом парсинг.
- Статус `429` — штатная ситуация, а не ошибка: пауза и повтор. Эндпоинты
  Wildberries регулярно отдают `429` и `5xx` при нормальной работе.

## Код

- Логирование только через `logging` (`get_logger`). Использование `print()`
  запрещено.
- Type hints на всех функциях и методах, включая возвращаемое значение.
- `common.py` — только функции, без классов.
- Таймзона всех расчётов дат и времени — `Europe/Moscow`. Даты хранить и
  сравнивать по московскому времени, «последние 7 дней» считаются от него.

## Структура

- Структура проекта плоская: модули лежат в корне, тесты — в `tests/`.
  Подпакеты с `__init__.py` не создавать.
- Каталога `output/` в репозитории нет: скрипты создают его при запуске через
  `Path("output").mkdir(exist_ok=True)`.

## Git

- Коммиты создаёт агент, без отдельного запроса, но только в feature-ветку.
  Обе части ТЗ завершены и находятся в master. Рабочая ветка не активна.
- Перед каждым коммитом проверять `git status` и убеждаться, что `.env`,
  `credentials.json`, `output/`, `task.md`, `vacancy.md` не попадают в индекс.
- `git add` только перечисленными файлами. Команды `git add .` и `git add -A`
  запрещены.
- Запрещены: `push` в `main`/`master`, `force push`, `rebase`, `commit --amend`.
- Прямой push в master с рабочей ветки запрещён. Merge feature-ветки в master и
  push merge-коммита разрешены только по явному указанию Tech Lead в тексте задачи.
- Прямые коммиты в master — только по явному указанию Tech Lead в тексте задачи.
- Переписывание истории и force push — только по явной санкции Tech Lead в
  тексте задачи. Вне такой санкции правила выше абсолютны.
- Сообщения коммитов — conventional commits: `chore:`, `feat:`, `fix:`,
  `test:`, `docs:`, `refactor:`.

## Проверка готовности

Любой этап считается завершённым только после последовательного успешного
выполнения:

```bash
pip install -r requirements.txt
python -c "import common"
python -m pytest
python <изменённый скрипт>
```

Коммит — только после того, как все проверки прошли.
