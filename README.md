# BRAUCHER — тестовое задание: аналитика Wildberries

## 1. О проекте

Две части отчётности по трём артикулам одного магазина на Wildberries
(шуруповёрт 386248405, коврик 147866642, монтажный пистолет 1138944672).

1. **Отзывы → сводка от языковой модели.** Собираем все отзывы покупателей по
   артикулам, отбираем содержательную выборку в фиксированный бюджет символов,
   формируем промпт и получаем разбор по каждому товару: что хвалят, на что
   жалуются, что улучшить, о чём говорят чаще всего.
2. **Воронка продаж → мини-дашборд в Google Таблице.** Выгружаем дневные
   показатели воронки за последние 7 дней (сегодняшний день исключён) и
   собираем таблицу: сырые данные по дням, сводная, где все показатели
   считаются формулами самой таблицы, и лист с методологией расчётов.

Стек: Python 3.11+, `requests`, `python-dotenv`, `gspread`, `pytest`. Других
пакетов нет — список в `requirements.txt` закрытый. Структура плоская: модули в
корне, тесты в `tests/`, `output/` создаётся скриптами и в репозиторий не
попадает.

## 4. Установка и запуск

```bash
python -m venv .venv
.venv\Scripts\activate                        # Windows (Linux/macOS: source .venv/bin/activate)
pip install -r requirements.txt
copy .env.example .env                         # Linux/macOS: cp .env.example .env
```

В `.env`:

- `WB_TOKEN` — токен Wildberries только на чтение;
- `NM_IDS` — артикулы через запятую (заглушки в `.env.example` уже проставлены);
- `GOOGLE_CREDENTIALS_PATH` — путь к JSON-ключу сервисного аккаунта Google;
- `SPREADSHEET_ID` — id таблицы-дашборда.

`credentials.json`, `.env`, `output/`, `task.md`, `vacancy.md` в репозиторий не
коммитятся (`.gitignore`). Сервисному аккаунту Google нужно выдать доступ к
таблице в роли «Редактор».

Порядок запуска:

```bash
python -m pytest                     # 79 тестов, без сети и токена
python fetch_reviews.py              # все отзывы -> output/reviews_raw.json, reviews.csv, reviews_stats.json
python build_ai_prompt.py            # промпт -> output/ai_prompt.txt
python split_ai_prompt.py            # части промпта + план отправки в чат
# далее вручную: отправляем части по плану, получаем ответ модели,
# сохраняем его в output/ai_summary.md (первой строкой — имя модели)

python setup_spreadsheet.py          # проверка доступа к таблице (credentials + SPREADSHEET_ID)
python fetch_sales_funnel.py         # воронка за 7 дней -> output/funnel_raw.json, funnel.csv, funnel_stats.json
python upload_to_sheets.py           # запись трёх листов + обратная сверка цифр
```

`fetch_reviews.py`, `fetch_sales_funnel.py` и `upload_to_sheets.py` идемпотентны:
пересобирают свои файлы и листы с нуля. `explore_*.py` — одноразовые скрипты
разведки, в пайплайне не участвуют.

## 6. Методология

### Отзывы (часть 1)

- **Полнота сбора.** Отзывы берутся обеими ветками эндпоинта
  (`isAnswered=true` и `isAnswered=false`), постранично, `take=1000`. Число
  собранных отзывов сверено со счётчиком API `countArchive` по каждому
  артикулу: совпадение 3 из 3, без единого расхождения — 7609 + 9354 + 368 =
  17 331 отзыв.
- **Срез в промпт.** Из 17 331 отзыва содержательных 5 220 (есть текст, плюсы
  или минусы). Целиком они не помещались: бюджет промпта 150 000 символов,
  поэтому выборка стратифицирована — первыми отзывы с минусами, затем с
  плюсами, затем только с текстом; бюджет делится между артикулами
  пропорционально объёму, отбор детерминирован (seed=42). Итог — 1712 отзывов
  (1016 / 646 / 50).
- **Смещение среза — оно есть и описано в самом промпте.** Жалобы отражены
  полностью: 612 отзывов с минусами из 612 по шуруповёрту и 453 из 453 по
  коврику. Похвала — только частью пула: 404 из 1685 и 193 из 903 отзывов с
  плюсами. Значит частота темы в срезе — это частота жалобы, а не частота темы
  среди всех отзывов; модель в промпте прямо предупреждена калибровать масштаб
  тем по распределению оценок товара, а не по числу упоминаний.
- **Ограничение, найденное при проверке.** В срезе 23 повторяющиеся строки
  отзыва (17 уникальных текстов, самый частый повторился 6 раз) — это короткие
  шаблонные комментарии вроде «Не работает» или «Отличный шурик». Дедупликация
  шла по `feedback_id`, а не по тексту: один и тот же текст от разных
  покупателей — это разные отзывы. На вывод влияет слабо (десятые доли
  процента), но упоминание такой темы в сводке слегка завышено.

### Воронка продаж (часть 2)

- **Период и масштаб.** `[2026-09-23; 2026-09-29]` по Москве, 7 дней,
  сегодняшний день исключён; 3 артикула × 7 дней = 21 дневная строка, по одной
  строке на пару артикул×день (дубли скрипт ловит и падает). Итоги за период:
  показы 29 429, заказы 1007 шт / 2 328 407 ₽, выкупы 412 шт / 976 729 ₽.
- **Выкупы уточняются задним числом.** Два сбора одного и того же окна с
  разницей примерно в час дали те же показы и заказы (16 470 и 264 у
  шуруповёрта), но выкупы 99 шт / 539 551 ₽ против 114 шт / 621 301 ₽:
  состояния заказов доходят до API с задержкой. Цифры последних дней окна —
  самые «плавающие», через сутки они обычно выше.
- **Показы = `openCount`.** Выбор не по документации, а по арифметике:
  тождество `round(cartCount / openCount * 100) = addToCartConversion`
  выполнилось на 21 из 21 дневных записей и не выполнилось ни для одного
  другого поля-кандидата.
- **CR день** = Заказы, шт / Показы (колонка M листа «Сырые данные»).
- **CR среднее, мин, макс** — по дневным CR без промежуточного округления:
  сначала среднее арифметическое точных дневных значений, округление одно в
  конце. Поэтому «CR среднее» — среднее по дням, а не отношение сумм за
  период. Если у артикула нет ни одного дня с числовым CR (показы нулевые во
  всех днях), в минимуме и максимуме стоит «—», а не 0: `MINIFS`/`MAXIFS`
  при отсутствии совпадений возвращают ноль как данные, и `IFERROR` этого не
  ловит, поэтому формулы сначала считают число строк с числовым CR.
- **Почему это разные числа.** По шуруповёрту 386248405 среднее по дням =
  1,66 %, а общее CR за период как отношение сумм = 264 / 16 470 = 1,60 %.
  Расхождение даёт неравномерность дней: среднее по дням даёт каждому дню
  равный вес, отношение сумм взвешивает день его показами. В сводной лежит
  среднее по дням, как требует ТЗ.
- **Средний чек** = Сумма заказов, ₽ / Заказы, шт (всего 2 328 407 / 1007 =
  2312,22 ₽). При нулевых заказах — «—», деления на ноль в формулах нет.
- **Сортировка** — по сумме выкупов ₽ по убыванию, а не по числу заказов:
  монтажный пистолет (136 заказов, 190 456 ₽ выкупов) стоит выше коврика
  (607 заказов, 164 972 ₽ выкупов), и это не ошибка, а выбранное определение.
- **buyoutPercent.** Цитата с листа «Методология»: buyoutPercent из API не
  воспроизводится ни одной формулой от дневных показателей (выкупы ₽ / заказы ₽
  — 0 из 21 записей; выкупы шт / заказы шт — 0 из 21; обе сразу — 2 из 21).
  Вероятная причина — знаменатель охватывает более ранние заказы, по которым
  уже истёк срок возврата (когортный расчёт); документального подтверждения нет.
  В расчётных метриках не используется, колонка «Выкуп, %» справочная.
- **Сверка после записи.** `upload_to_sheets.py` читает сводную дважды
  (значения и формулы) и сравнивает с `funnel_stats.json`: 36 проверок,
  0 расхождений; целые и рубли — строго, средние — с допуском 0,01. Отчёт —
  `artifacts/part2/sheets_verification.json`. Если проверка периода в
  `funnel_stats.json` не пройдена, публикация запрещена и скрипт останавливается.
- **Диапазоны формул.** Построчные агрегаты и ИТОГО смотрят на целые столбцы
  «Сырых данных» (`SUMIFS`/`AVERAGEIFS`/`MINIFS`/`MAXIFS` с фильтром по
  артикулу, `SUM`/`AVERAGE`/`MIN`/`MAX` по всему столбцу), жёстких видов
  `C2:C4` или `M2:M22` нет: новый артикул или новый день попадает в итог
  автоматически, и итог не может разойтись со строками артикулов.

## 7. Ход мыслей и принятые решения

- **Эндпоинт отзывов не отдаёт данные без `isAnswered`.** Первый запрос без
  поля вернул `400 ... isAnswered (field required)`, поэтому сбор идёт двумя
  ветками. Побочный, но полезный факт: ветка `isAnswered=false` пуста —
  неотвеченных отзывов у магазина нет, и «все отзывы» собираются одной веткой.
- **Счётчику API сначала не поверил.** Гипотеза была в том, что `countArchive`
  считает архив по всему магазину, а не по артикулу. Зонд: базовый замер из
  дампа и один запрос с другим `nmId` и другой веткой — счётчик изменился
  вместе с `nmId`. Выводу по двум запросам не поверил, оставил гипотезой:
  доказательством стала сверка после полного сбора — число собранных отзывов
  с `countArchive`, 3 из 3 точных совпадения, и этот вердикт записан в
  `reviews_stats.json`, а не оставлен на слово.
- **Имена полей брал только из сырых дампов.** `openCount` как «показы» — не
  догадка по документации, а поле, замкнутое на `addToCartConversion` на всех
  21 записи. Тело запроса к воронке тоже подбиралось по сообщениям API:
  `nmIds`, `selectedPeriod.start`, `aggregationLevel` — каждое изменение
  продиктовано конкретным `400`, а не перебором вариантов наугад.
- **Молчаливый баг локализации в Google Таблице.** Формулы записывались через
  `USER_ENTERED` и давали `#ERROR!`, при этом ошибок API не было. Проба
  `=SUM(1,2)` вернула число `1.2`: локаль таблицы `ru_RU`, где запятая —
  десятичный разделитель, а аргументы формул разделяются точкой с запятой.
  Разделитель теперь выводится из локали таблицы (`formula_separator`), а не
  зашит в код.
- **Промпт не дошёл до модели целиком.** 180 754 символа одним сообщением чат
  обрезал. Разбил на 4 части по 50 000 символов с проверяемой склейкой: строка
  отзыва — атомарная (переносы внутри текста свёрнуты, иначе отзыв разъезжался
  бы по двум частям), а после сборки проверяется, что ни одна строка не
  потерялась и не продублировалась. Ключевая строка плана — «данные
  закончились»: анализ начинается только после неё.
- **Утечка персональных данных в тестовых фикстурах.** Проверка перед коммитом
  нашла реальные имена покупателей и поставщика в комментарии теста: список
  «запрещённых строк» сам содержал те имена, от которых должен был защищать.
  Фикстуры обезличены (`userName` → «Тест», ссылки и приветствия вычищены),
  проверка стала структурной (ищем не имена, а поля), история по явной санкции
  переписана, а в `AGENTS.md` добавлено правило про переписывание истории и
  force push.
- **Всё считается по Москве.** Даты хранятся и сравниваются по московскому
  времени (`common.MOSCOW_TZ`); смещение фиксированное (+03:00), потому что
  `zoneinfo` на Windows без `tzdata` не находит `Europe/Moscow`, а новые
  зависимости запрещены — с 2014 года переходов на летнее время в Москве нет.
- **После приёмки прогнал ревью кода и независимый аудит формул.** Числа
  сошлись (45 метрик пересчитаны из `funnel.csv` двумя путями независимо), но
  аудит нашёл то, что не видно на удачных данных: проверка периода считала
  уникальные даты и пропускала строку-дубль, а её результат только писали в
  лог; `MINIFS`/`MAXIFS` дают `0` вместо «—» на артикуле без показов; строка
  ИТОГО зависела от жёстких диапазонов; сверка падала на законных `null`
  и падала уже после записи в таблицу. Всё это исправлено, на
  вырожденных данных добавлены тесты, а текст методологии больше не содержит
  ни одной цифры, вшитой литералом, — все они выводятся из `funnel_stats.json`.

## 8. Что улучшил бы в проде

- **Плановый запуск вместо ручного:** cron или облачные функции (Cloud Run
  Jobs / Cloud Functions) по расписанию, секреты — в менеджере секретов, а не
  в `.env`.
- **Инкрементальная загрузка:** собирать только новые дни воронки и новые
  отзывы по курсору, а не перезаливать 17 331 отзыв и 21 строку целиком; у
  эндпоинта отзывов для этого есть `createdDate` и `updatedDate`.
- **Хранение в БД:** PostgreSQL или BigQuery как источник истины, таблица —
  лишь витрина. Сейчас история живёт в файлах `output/`, и динамику между
  запусками сравнить нельзя.
- **Алертинг:** уведомления о падении сборов (401/403, пустой ответ там, где
  ждём данные), о пробое лимитов (429 чаще штатного) и о провале сверки цифр
  после записи — сейчас неудачная сверка это `exit 1`, который видит только
  запускавший.
- **Telegram-бот с еженедельной сводкой:** по понедельникам присылать по трём
  артикулам итоги недели (заказы, выкупы, CR, средний чек, отклонение от
  прошлой недели) и топ-тем из отзывов. Данные для этого уже нормализованы и
  лежат в устойчивом формате CSV/JSON.
